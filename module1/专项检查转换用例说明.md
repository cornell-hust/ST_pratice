# 专项自动化检查转换用例说明（CRON-UT-041—050）

> 本文说明模块一中 **5 条专项自动化检查**如何转换为 **10 条账本参数化用例**（CRON-UT-041—050），
> 并逐条解释其输入、预期、设计依据与断言实现。
> 相关文件：`testdata/cron_cases.json`（账本）、`tests/test_croniter.py`（实现）、
> `testcases/附录1-测试用例清单v3.xlsx`（清单第 13、26—28、37—42 行）。

## 一、转换背景

**转换前的问题**：专项自动化检查以 5 个独立测试函数的形式存在（`test_match_and_range`、
`test_match_range_and_is_valid`、`test_return_types_seconds_and_year`、
`test_timezone_dst_zoneinfo`、`test_exception_inputs`），其输入与预期**写死在测试代码中**，
游离于账本之外。由此产生三个不一致：

1. **违背"数据单一来源"原则**——账本只覆盖表达式解析与迭代类用例，专项检查的数据在代码里；
2. **无法逐条追溯**——变更检查内容必须改代码，附录一清单中也没有对应条目；
3. **统计口径割裂**——只能表述为"31 条清单用例 + 5 条专项检查"，无法与其他用例统一编号管理。

**转换结果**：5 个独立函数被删除，其断言拆分为 **10 条账本用例（CRON-UT-041—050）**，
全部纳入附录一清单 v3（清单用例总数 31 → 41），与其他用例共用同一套编号与追溯链路。

## 二、转换映射关系

| 原独立测试函数 | 检查内容 | 转换后的用例 | 条数 |
|---|---|---|---|
| `test_exception_inputs` | 非法起始类型、日期越界 | CRON-UT-044、CRON-UT-041 | 2 |
| `test_return_types_seconds_and_year` | 默认返回类型、秒级表达式合法性 | CRON-UT-042、CRON-UT-049 | 2 |
| `test_timezone_dst_zoneinfo` | 夏令时切换日的时区正确性 | CRON-UT-043 | 1 |
| `test_match_and_range` | 时刻匹配命中/未命中、窗口触发点个数 | CRON-UT-045、CRON-UT-046、CRON-UT-050 | 3 |
| `test_match_range_and_is_valid` | 时段匹配含/不含触发点、表达式合法性 | CRON-UT-047、CRON-UT-048、CRON-UT-049 | 3（049 与上行共用） |
| **合计** | — | **041—050** | **10 条（唯一）** |

> 注：CRON-UT-049 同时对应两个原函数的检查意图（合法性校验与秒级表达式解析），
> 转换时合并为一条用例，避免重复计数，因此 5 个函数最终得到 10 条唯一用例。

**未转换的断言及原因**（按"不与清单原有用例重复"的要求舍弃）：

| 原断言 | 舍弃原因 |
|---|---|
| `croniter.is_valid('0 0 * * *')` → True | 与 CRON-UT-001—008 同为"合法表达式类"等价类，重复 |
| `not croniter.is_valid('not cron')` → False | 与 CRON-UT-009（非法文本 `bad expr`）同为"非法表达式类"，重复 |
| `nxt.tzinfo == tz`（时区对象一致性） | 见 CRON-UT-043 说明：转换后改为按时刻瞬时点比对，未保留 tzinfo 对象一致性断言 |

## 三、转换规则

1. **一条断言 = 一条用例**：原函数中以 `assert` 表达的独立判定拆分为独立账本记录。
   例如 `test_match_and_range` 中的"命中"与"未命中"两个断言，拆为 CRON-UT-045 与 CRON-UT-046。
2. **数据入账本**：表达式、起始时间、时段结束时间、预期值等全部写入 `testdata/cron_cases.json`，
   测试代码不再出现任何具体输入或预期字面量。
3. **断言按字段分发**：不再新增测试函数，由既有参数化函数按账本字段选择断言方式——
   `check` 字段区分 `match` / `match_range` / `is_valid` / `range`，
   `ret_type` 区分返回值类型检查，`tz` 区分时区构造，`start: "object"` 区分异常输入。
4. **设计方法归位**：`category` 只表达测试设计方法——045—049 属**等价类划分**
   （时刻命中/未命中、窗口含/不含触发点、合法表达式三组等价类），
   041 属等价类（非法表达式类），042—044 属**边界值分析**，050 属**场景法**；
   接口名（match/range）不再作为分类，改由 `check` 字段承载。
5. **编号连续**：续接 CRON-UT-040 顺延编号，不改动既有编号。

## 四、逐条用例说明

### CRON-UT-041 日期字段越界应抛标准错误

- **来源**：`test_exception_inputs` 中的 `croniter('0 0 32 * *', ...)` 断言
- **设计方法**：等价类划分（非法表达式类） · **账本类别**：`equivalence`
- **输入**：`expr = 0 0 32 * *`（日期字段 32 超出 1—31 值域）
- **预期输出**：抛出 `CroniterBadCronError`，信息为 `[0 0 32 * *] is not acceptable, out of range`
- **设计依据**：cron 日期字段的合法值域为 1—31，"32"是**刚好越界**的代表值。
  该用例与 CRON-UT-011（分钟 60 越界）配对，分别验证日期与分钟两个字段的越界拒绝，
  确认非法输入不会静默通过、且必须走 croniter 自定义异常家族。
- **断言实现**：`test_parser_equivalence` 中 `valid=false` 分支 → `pytest.raises(CroniterBadCronError)`

### CRON-UT-042 6 段秒级表达式默认返回 float 时间戳

- **来源**：`test_return_types_seconds_and_year` 中的 `isinstance(get_next(), float)` 断言
- **设计方法**：边界值分析（返回值类型） · **账本类别**：`boundary`
- **输入**：`expr = */30 * * * * *`（6 段，含秒字段，每 30 秒），
  `start = 2024-01-01T00:00:00+00:00`
- **预期输出**：`get_next()` 返回 `float` 类型，实测值 `1704067201.0`（秒级 Unix 时间戳）
- **设计依据**：croniter 的 `get_next()` 在不指定 `ret_type` 时按表达式段数决定返回类型——
  5 段返回 float 时间戳、6/7 段（含秒）返回 datetime。这是**易被误解的接口约定**：
  调用方若想统一拿到 datetime 必须显式传参。该用例锁定"默认返回 float"的行为，防止升级时静默变更。
- **断言实现**：`test_next_boundaries` 中 `ret_type == "float"` 分支 → `isinstance(..., float)`

### CRON-UT-043 夏令时切换日的时区正确性

- **来源**：`test_timezone_dst_zoneinfo`
- **设计方法**：边界值分析（夏令时边界） · **账本类别**：`boundary`
- **输入**：`expr = 0 2 * * *`（每天 02:00），`start = 2024-03-09T00:00:00-05:00`，
  时区 `America/New_York`
- **预期输出**：`2024-03-09 02:00:00-05:00`（纽约时间，UTC 偏移 -05:00）
- **设计依据**：美国 2024 年 3 月 10 日凌晨 02:00 因夏令时开始**直接跳到 03:00**——
  "02:00"这一时刻在切换日并不存在，是时区计算最典型的边界陷阱。起点刻意选在**切换前一天**，
  验证程序在 DST 边界附近仍能算出正确的触发时刻与 UTC 偏移（实测返回
  `2024-03-09 02:00 America/New_York`，偏移 -05:00）。
- **断言实现**：`test_next_boundaries` 中 `tz` 字段分支 → 用 `ZoneInfo` 重建起始时间后，
  与账本预期值比对（datetime 相等性按 UTC 瞬时点判定，偏移错误或日期偏移会立即失败）
- **转换时的两处变化**（如实记录）：
  1. 原弱断言 `assert nxt.day in (9, 10)` **收紧为精确值比对**（必须恰为 03-09 02:00），
     避免"范围断言"掩盖潜在偏差；
  2. 原断言 `nxt.tzinfo == tz`（返回对象的时区**对象**必须是传入的 ZoneInfo）**未保留**——
     转换后按时刻比对，"返回同一瞬时点但 tzinfo 类型不同"的情形不再被检出，属已知的覆盖弱化。

### CRON-UT-044 非法起始时间类型应抛异常

- **来源**：`test_exception_inputs` 中的 `croniter('* * * * *', object())` 断言
- **设计方法**：异常测试（非法输入类型） · **账本类别**：`boundary`
- **输入**：`expr = * * * * *`，起始时间为 `object()`（非 datetime 类型）
- **预期输出**：抛出 `TypeError` 或 `ValueError`
- **设计依据**：验证公开 API 的**输入类型防护**——传入错误类型的起始时间时，
  程序应快速失败并给出 Python 标准异常，而不是在后续计算中产生难以定位的隐式错误。
  断言接受两种异常类型，是因为不同版本实现可能抛 `TypeError`（类型检查）或
  `ValueError`（解析失败），两者都属"合理拒绝"。
- **断言实现**：`test_next_boundaries` 中 `start == "object"` 分支 → `pytest.raises((TypeError, ValueError))`

### CRON-UT-045 时刻匹配命中（match 命中类代表）

- **来源**：`test_match_and_range` 中的 `croniter.match('0 0 * * *', dt)`
- **设计方法**：等价类划分（时刻命中类） · **账本类别**：`equivalence`，`check = match`
- **输入**：`expr = 0 0 * * *`（每天 0 点），时刻 `2024-01-01T00:00:00+00:00`
- **预期输出**：`True`（该时刻符合规则）
- **设计依据**：`match` 的输入域是所有时刻，按"是否符合规则"划分等价类，本条为**命中类代表**。
  时刻刻意取在触发点本身——最容易与"边界包含性"实现错误冲突的位置
  （若实现把触发点判为不匹配，本用例立即失败）。
- **断言实现**：`test_parser_equivalence` 中 `check == "match"` 分支 → 布尔值比对

### CRON-UT-046 时刻匹配未命中（match 未命中类代表）

- **来源**：`test_match_and_range` 中的 `assert not croniter.match('0 0 * * *', dt + 1min)`
- **设计方法**：等价类划分（时刻未命中类） · **账本类别**：`equivalence`，`check = match`
- **输入**：`expr = 0 0 * * *`，时刻 `2024-01-01T00:01:00+00:00`（触发点后 1 分钟）
- **预期输出**：`False`（该时刻不符合规则）
- **设计依据**：与 CRON-UT-045 成对，构成 `match` 的两个等价类。
  取值刻意选在**触发点后 1 分钟**（最邻近的"干扰点"），若实现存在
  "容差过宽"（如按分钟粒度取整比较）或"边界包含性"错误，本用例必然暴露。
- **断言实现**：同 045

### CRON-UT-047 时段匹配：窗口内存在触发点

- **来源**：`test_match_range_and_is_valid` 中的 `croniter.match_range('0 0 * * *', dt, dt+1day)`
- **设计方法**：等价类划分（窗口含触发点类） · **账本类别**：`equivalence`，`check = match_range`
- **输入**：`expr = 0 0 * * *`，窗口 `2024-01-01T00:00:00+00:00` 至 `2024-01-02T00:00:00+00:00`（恰好一天）
- **预期输出**：`True`
- **设计依据**：`match_range` 按"窗口内是否存在触发点"划分等价类，本条为**含有类代表**。
  窗口取为整一天，两端点均为触发点，同时验证了**端点包含性**（若实现使用开区间会判为 False）。
- **断言实现**：`test_parser_equivalence` 中 `check == "match_range"` 分支 → 布尔值比对

### CRON-UT-048 时段匹配：窗口内不存在触发点

- **来源**：`test_match_range_and_is_valid` 中的 `assert not croniter.match_range('0 1 * * *', dt, dt+30min)`
- **设计方法**：等价类划分（窗口不含触发点类） · **账本类别**：`equivalence`，`check = match_range`
- **输入**：`expr = 0 1 * * *`（每天 01:00），窗口 `2024-01-01T00:00:00+00:00` 至 `00:30:00+00:00`
- **预期输出**：`False`
- **设计依据**：与 CRON-UT-047 成对。窗口刻意选为 00:00—00:30，而规则的触发点为 01:00——
  触发点**紧邻窗口之外**，用于检验实现不会把窗口外的触发点错误计入（边界判定偏移会立即失败）。
- **断言实现**：同 047

### CRON-UT-049 秒级表达式的合法性校验

- **来源**：`test_match_range_and_is_valid`（`is_valid` 断言）与
  `test_return_types_seconds_and_year`（`second_at_beginning=True` 断言）合并
- **设计方法**：等价类划分（合法表达式类） · **账本类别**：`equivalence`，`check = is_valid`
- **输入**：`expr = 0 0 0 1 1 *`（6 段），`second_at_beginning=True`
- **预期输出**：`True`
- **设计依据**：6 段表达式默认按"秒在最后"解析，而 `second_at_beginning=True` 时按"秒在最前"解析。
  同一字符串在两种解析模式下语义不同，本用例验证**显式指定解析模式时能被正确识别为合法**，
  与 CRON-UT-010（字段数不足）共同覆盖 6 段/多段表达式的接受边界。
- **断言实现**：`test_parser_equivalence` 中 `check == "is_valid"` 分支 →
  `is_valid(expr, second_at_beginning=...)` 布尔值比对

### CRON-UT-050 窗口内连续触发序列枚举

- **来源**：`test_match_and_range` 中的 `len(list(croniter_range(dt, dt+3min, '* * * * *'))) == 4`
- **设计方法**：场景法（窗口内连续触发序列） · **账本类别**：`scenario`，`check = range`
- **输入**：`expr = * * * * *`，窗口 `2024-01-01T00:00:00+00:00` 至 `00:03:00+00:00`
- **预期输出**：恰好 4 个触发点——`00:00、00:01、00:02、00:03`（均为 UTC）
- **设计依据**：验证 `croniter_range` 在一次调用中枚举完整触发序列的场景行为，
  重点检验**窗口两端点的包含性**（首尾都应计入）与**个数与区间长度的对应关系**。
  端点处理错误（多算/少算一个）或迭代终止条件错误在此用例上必然失败。
- **断言实现**：`test_scenarios` 中 `check == "range"` 分支 →
  `len(list(croniter_range(start, end, expr))) == count`
